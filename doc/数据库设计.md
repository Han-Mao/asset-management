# 二、统一约定

所有表建议：

```text
主键：BIGINT
时间：TIMESTAMP WITH TIME ZONE
金额：NUMERIC(12,2)
状态：VARCHAR + CHECK
```

不建议一开始大量使用 PostgreSQL ENUM。

原因很简单：

> 后面改状态时，VARCHAR + CHECK 更容易维护。

例如：

```sql
status VARCHAR(20) NOT NULL
CHECK (status IN ('IN_STOCK', 'BORROWED', 'REPAIRING', 'PENDING_REPAIR', 'PENDING_SCRAP', 'SCRAPPED'))
```

这是最重要的表。

```sql
                'PENDING_SCRAP',

    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
```

# 十三、这里加一个非常重要的约束

正常情况下：

> 一台资产只能存在一个“当前领用记录”。

PostgreSQL 可以用部分唯一索引：

```sql
CREATE UNIQUE INDEX uq_active_asset_assignment
ON asset_assignment(asset_id)
WHERE status IN ('ACTIVE', 'OVERDUE');
```

这样从数据库层面就能防住：

```text
同一台电脑
同时被两个人领用
```

不过这里还要配合审批事务中的行锁。

也就是：

```text
数据库约束
+
SELECT FOR UPDATE
+
业务状态校验
```

三层保障。

# 十八、几个业务规则不要放在数据库 CHECK 里

这些交给 Service 层。

例如：

```text
资产已报废
→ 不能申请领用

资产已领用
→ 不能再次申请

资产维修中
→ 不能领用

申请已经审批
→ 不能再次审批

已归还
→ 不能再次归还
```

这种属于**业务状态机规则**。

不要把所有东西硬塞进 SQL。

# 十九、审批事务正式确定

这里建议你后面直接按这个逻辑写。

```python
async def approve_application(application_id, approver_id):

    async with db.begin():

        application = await get_application_for_update(
            application_id
        )

        if application.status != "PENDING":
            raise BusinessError("申请已处理")

        asset = await get_asset_for_update(
            application.asset_id
        )

        if asset.status != "IN_STOCK":
            raise BusinessError("资产当前不可领用")

        application.status = "APPROVED"
        application.approver_id = approver_id
        application.approval_time = now()

        asset.status = "BORROWED"

        assignment = AssetAssignment(
            asset_id=asset.id,
            user_id=application.applicant_id,
            application_id=application.id,
            expected_return_time=application.expected_return_time
        )

        db.add(assignment)

        notification = create_notification(...)

        db.add(notification)

        create_operation_log(...)
```

最终：

```text
一个事务
    ↓
审批成功
    ↓
资产状态更新
    ↓
领用记录创建
    ↓
通知创建
    ↓
操作日志创建
```

任何一步失败：

```text
ROLLBACK
```

# 二十、为什么这里不用 Redis 锁？

面试时可能会有人问：

> 为什么不用 Redis 分布式锁？

你的回答可以是：

> “这个场景核心数据就在 PostgreSQL，我优先使用数据库事务和行级锁解决资产审批并发问题。因为审批本身就是数据库事务操作，用 SELECT FOR UPDATE 锁住具体资产记录比较直接，而且最终还有唯一索引做兜底。Redis 锁不是不能做，但对于一周项目来说没必要引入额外一致性复杂度。”

这个回答比较稳。

# 二十二、提醒去重怎么处理

这里我建议增加一个**简单的 Redis 去重机制**，而不是再增加数据库表。

例如：

```text
asset:reminder:{assignment_id}:7d
asset:reminder:{assignment_id}:1d

```

设置 TTL。

这样：

```text

→ 不再发

→ 可以再次发
```

一周项目很适合这种实现。

# 二十五、为什么 `asset` 不直接保存 borrower_id？

这是非常关键的设计问题。

不要设计成：

```text
asset
├── owner_id
├── borrow_time
└── return_time
```

因为这样历史记录会被覆盖。

正确的是：

```text
asset
     ↓
当前状态

asset_assignment
     ↓
历史领用关系
```

例如：

```text
Asset 001
    │
    ├── Assignment 001 张三
    ├── Assignment 002 李四
    └── Assignment 003 王五
```

资产详情页就能展示完整历史。

```text
100~200 条
```

不要只准备 5 台。

首页图表、分页、筛选、导出都会更像真实系统。

# 二十九、Demo 数据要故意准备几种特殊状态

这点非常重要。

数据库初始化的时候，至少准备：

```text
在库       30%
已领用     50%
维修中      5%
待维修      3%
待报废      2%
已报废     10%
```

然后准备：

```text
即将30天到期
即将7天到期
明天到期
已经逾期
```

再准备：

```text
待审批申请
已通过申请
已驳回申请
```

这样你演示的时候所有功能都有数据。

# 三十、现在数据库层已经可以冻结

最终开发蓝图：

```text
                ┌─────────────┐
                │ PostgreSQL  │
                └──────┬──────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
      用户权限        资产业务        系统能力
        │              │              │
        ▼              ▼              ▼
    sys_user        asset          notification
    sys_role        category       operation_log
    permission      application
    user_role       assignment
    role_permission repair
```

接下来就不要再随意改表结构了。

**下一层直接进入 FastAPI 后端设计**，顺序应该是：

```text
数据库 Model
      ↓
Pydantic Schema
      ↓
Repository
      ↓
Service
      ↓
API Router
      ↓
JWT + RBAC
      ↓
Celery 定时提醒
```

其中最值得先写的是这 **5 个 Service**：

```text
AuthService
AssetService
ApplicationService
AssignmentService
NotificationService
```

然后再补：

```text
RepairService
DashboardService
ImportExportService
```

这样代码量会非常可控，也能保持架构清晰。
