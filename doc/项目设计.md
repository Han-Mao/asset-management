# 项目设计

好，我们先把 **数据库表结构 + 页面原型 + API 清单** 固定下来，后面写代码就按这个版本走，避免开发过程中反复改数据库和接口。

我建议这一版遵循一个原则：

> **业务完整优先，技术不过度设计。**

一周作业直接采用 **8 张核心表 + 3 张增强表**。

------

# 一、先确定系统边界

最终系统名称可以叫：

> **IT资产全生命周期管理系统**

核心闭环：

```text
用户登录
   ↓
查看资产
   ↓
发起领用申请
   ↓
管理员审批
   ↓
资产变为“已领用”
   ↓
到期提醒
   ↓
归还 / 维修
   ↓
重新入库
   ↓
报废
```

管理员负责：

```text
资产
用户
审批
维修
统计
导入导出
消息
日志
```

普通用户负责：

```text
查看资产
申请领用
查看自己的申请
查看自己的设备
查看消息
申请维修
```

# 二、数据库设计

## 1. 用户表 `sys_user`

```text
sys_user
├── id
├── username
├── password_hash
├── real_name
├── email
├── phone
├── department_id
├── status
├── created_at
└── updated_at
```

字段设计：

| 字段          | 类型         | 说明           |
| ------------- | ------------ | -------------- |
| id            | BIGINT       | 主键           |
| username      | VARCHAR(50)  | 登录账号，唯一 |
| password_hash | VARCHAR(255) | 密码           |
| real_name     | VARCHAR(50)  | 姓名           |
| email         | VARCHAR(100) | 邮箱           |
| phone         | VARCHAR(20)  | 手机           |
| department_id | BIGINT       | 部门           |
| status        | SMALLINT     | 1正常 0禁用    |
| created_at    | TIMESTAMP    | 创建时间       |
| updated_at    | TIMESTAMP    | 更新时间       |

这里不要直接做 `is_admin`。

因为后面已经有角色表了。

# 六、核心资产表

## 6. `asset`

这是整个系统最重要的一张表。

```text
asset
├── id
├── asset_code
├── asset_name
├── category_id
├── brand
├── model
├── serial_number
├── purchase_date
├── purchase_price
├── warranty_expire_date
├── status
├── location
├── supplier
├── remark
├── created_at
└── updated_at
```

推荐字段：

| 字段                 | 说明     |
| -------------------- | -------- |
| asset_code           | 资产编号 |
| asset_name           | 设备名称 |
| category_id          | 设备类型 |
| brand                | 品牌     |
| model                | 型号     |
| serial_number        | 序列号   |
| purchase_date        | 采购日期 |
| purchase_price       | 采购价格 |
| warranty_expire_date | 保修到期 |
| status               | 当前状态 |
| location             | 存放位置 |
| supplier             | 供应商   |
| remark               | 备注     |

### 资产状态

建议固定成枚举：

```text
IN_STOCK       在库
BORROWED       已领用
REPAIRING      维修中
PENDING_REPAIR 待维修
PENDING_SCRAP  待报废
SCRAPPED       已报废
```

一周版本不要再增加十几个状态。

## 7. `asset_application`

```text
asset_application
├── id
├── application_no
├── applicant_id
├── asset_id
├── reason
├── apply_time
├── expected_return_time
├── status
├── approver_id
├── approval_time
├── approval_remark
├── created_at

```

状态：

```text
PENDING
待审批

APPROVED
已通过

REJECTED
已驳回

CANCELLED
已取消
```

这里我建议：

> **一个申请对应一台资产**

不要一上来设计“一个申请里面有 30 个资产”。

因为这样审批逻辑、库存并发控制都会复杂很多。

一周 Demo 完全可以：

> 用户申请一台设备 → 管理员审批。

# 八、正式领用记录

申请通过以后，需要产生正式领用记录。

## 8. `asset_assignment`

```text
asset_assignment
├── id
├── asset_id
├── user_id
├── application_id
├── assign_time
├── expected_return_time
├── actual_return_time
├── status
├── remark
└── created_at
```

这里解决一个关键问题：

### 为什么不直接把 `user_id` 放到 asset？

因为一个资产可能经历：

```text
张三领用
 ↓
归还
 ↓
李四领用
 ↓
维修
 ↓
再次给王五领用
```

所以：

```text
asset
```

记录“当前状态”。

而：

```text
asset_assignment
```

记录“历史领用关系”。

```text
                       │
                     领用
                       ↓
                 ┌────────────┐
                 │   已领用   │
                 └─────┬──────┘
                    │       │
                  归还      报修
                    │       ↓
                    │   ┌────────┐
                    │   │维修中  │
                    │   └───┬────┘
                    │       │
                    │     完成
                    │       ↓
                    └────→ 在库

      │
      ↓
   待报废
      │
      ↓
    已报废
```

# 十四、领用审批状态

```text
待审批
  │
  ├────→ 已通过
  │
  └────→ 已驳回
```

通过的时候：

```text
asset_application.status = APPROVED

asset.status = BORROWED

创建 asset_assignment

```

这四个操作建议放到**同一个数据库事务**里面。

# 三十一、到期提醒 API

这一块不建议给前端暴露“触发定时任务”的核心逻辑。

后端定时执行：

```text
Celery Beat
   ↓
expire_reminder_task()
```

内部：

```text
查询未来30天到期
        ↓
判断7天/1天/逾期
        ↓
检查是否重复提醒
        ↓
创建 notification
        ↓
普通用户发送邮件
        ↓
管理员发送站内信
```

如果为了演示，可以额外提供管理员接口：

```text
POST /api/system/reminders/test
```

开发环境可以手动触发。

生产逻辑仍然由 Celery 定时执行。

# 三十三、一个非常重要的权限细节

普通用户不能直接修改：

```text
asset.status
asset.owner
asset_assignment
```

比如前端传：

```json
{
  "status": "BORROWED"
}
```

后端也不能接受。

正确方式是：

```text
用户申请
 ↓
审批通过
 ↓
后端修改资产状态
```

也就是说：

> **业务状态必须由业务动作驱动，而不是让前端直接修改。**

这个点在面试里很好讲。

------

# 三十四、最关键的事务

审批接口：

```text
POST /api/applications/{id}/approve
```

后端逻辑建议定成：

```text
开始事务

1. 查询申请
2. 检查申请状态 == PENDING

3. 锁定资产记录

4. 检查资产状态 == IN_STOCK

5. 修改申请状态 = APPROVED

6. 修改资产状态 = BORROWED

7. 创建 asset_assignment

8. 创建站内信

9. 创建操作日志

提交事务
```

这样即使两个管理员同时审批，也不会把同一个资产重复领出去。
