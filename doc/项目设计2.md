# 三十四、JWT 里面放什么

不要把大量用户信息塞进去。

建议：

```json
{
  "sub": "10001",
  "exp": 1780000000
}
```

`sub` 就是用户 ID。

角色、权限从数据库或者缓存获取。

这样用户权限变更以后不用重新生成大量 Token。

# 四十、创建申请逻辑

用户点击“申请领用”：

```text
1. 查询资产
2. 判断资产存在
3. 判断资产状态 == IN_STOCK
4. 判断用户是否有未完成的同类申请
5. 创建 application
6. 发送管理员通知
7. 记录操作日志
```

这里不直接改变资产状态。

资产仍然：

```text
IN_STOCK
```

只有审批通过以后才：

```text
BORROWED
```

------

# 四十一、为什么申请时不锁资产？

因为：

> “申请”不代表“获得资产”。

例如：

```text
张三申请 ThinkPad
李四也申请 ThinkPad
```

管理员后面决定给谁。

真正需要抢占库存的是：

```text
审批通过
```

所以锁应该放在审批阶段。


# 四十三、`SELECT FOR UPDATE`

Repository：

```python
async def get_asset_for_update(
    self,
    asset_id: int
):
    result = await self.session.execute(
        select(Asset)
        .where(Asset.id == asset_id)
        .with_for_update()
    )
    return result.scalar_one_or_none()
```

两个管理员同时操作：

```text
Admin A                  Admin B

锁 Asset 001             等待
    ↓
检查 IN_STOCK
    ↓
改成 BORROWED
    ↓
提交
                         获得锁
                           ↓
                       检查发现
                       BORROWED
                           ↓
                         拒绝
```

这样就解决并发问题。

# 四十四、归还流程

接口：

```text
POST /api/assignments/{id}/return
```

流程：

```text
1. 查询 assignment
2. 检查 ACTIVE / OVERDUE
3. 锁定 asset
4. assignment → RETURNED
5. actual_return_time = now()
6. asset → IN_STOCK
7. 创建操作日志
```

如果设备归还以后发现故障：

```text
归还
 ↓
PENDING_REPAIR
```

而不是直接重新变成 `IN_STOCK`。

这可以根据你的业务来处理。

# 五十一、逾期不要只发一次

例如：

```text
9月28日 到期
```

到了：

```text
9月29日
```

资产应该自动显示：

```text
OVERDUE
```

但这里我建议：

**不要修改 asset.status 为 OVERDUE。**

因为：

```text
asset.status = BORROWED
```

表达的是资产当前状态。

而：

```text
assignment.status = OVERDUE
```

表达的是：

> 领用关系已经逾期。

这样数据语义更清楚。

所以：

```text
Asset
BORROWED

Assignment
OVERDUE
```

完全可以共存。

# 六十一、删除资产怎么处理

**不要允许删除已领用、维修中、已经产生历史记录的资产。**

例如：

```text
在库
且从来没有领用
```

可以删除。

如果：

```text
已领用
```

应该：

```text
报废
```

而不是：

```text
DELETE
```

这样历史数据不会消失。

实际上后台的“删除资产”更准确地说：

> 删除未投入使用的错误资产记录。

```text

```

```text

```

这样误删还有恢复空间。

不过一周项目可以先不做，避免扩大工作量。
